# Introduction

“Refactoring by Term Multiplexing” or RTM is here an architectural pattern for authoring our formal proof.

In traditional mathematical proving, a proof is often treated as a monolithic script. If an intermediate lemma breaks or is incomplete, the entire theorem fails to compile.

In programming a problem is semantically more loosely treated, so that dependencies risk in drifting away from the original proof target. 



 CRC solves this by strictly decoupling the “Public Contract” (the theorem statement) from the “Internal Proof State” (the mechanics) using “Routing” from the start.

This allows a proof to be authored in a process that may not halt but is more robust mathematically. Once the statement and the contract is aligned and immutable, high-level axiomatic assumptions and progressively decompressing them into finer, mechanically rigorous layers without ever breaking the terminal `QED` certification.

# The Architectural Components

A CRC proof pipeline requires four distinct topological layers:

The Contract (Premises): The immutable, public-facing definition of the problem. This file contains the imports, domains, and the exact proposition to be proved. It contains no proof logic.

The Phases (Curried Logic):
    
- Phase 0 is entirely axiomatic (assuming the conclusion).
- Phase N is completely mechanically resolved (pure formal logic / lambda calculus).
- Intermediate phases discharge higher-level axioms into smaller, more granular sub-axioms.
- The Switch (Router): A multiplexer file that acts as the single source of truth for the active proof state. It aliases the current working phase to a standard name.
- The Certification (QED): The terminal file. It imports the Router and applies the active phase to the Contract.


## Why This Methodology Works

| Feature | Traditional Monolithic Proofs | Continuous Refactoring by Currying (CRC) |
| :--- | :--- | :--- |
| **State** | Binary (Broken / Compiled) | Continuous (Always Compiles, varying depth) |
| **Traceability** | Relies on code comments. | `Print Assumptions` acts as a structural `git diff` for logical depth. |
| **Collaboration** | Highly blocking. One missing lemma kills the project. | Highly parallel. A Phase 1 axiom acts as an API contract for another team to solve in Phase 2. |
| **Cognitive Load** | Low-level type theory simultaneously. | One “bracket” of semantic logic at a time. |
